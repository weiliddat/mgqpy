# Offline MongoDB filter matchers: compatibility and performance

This directory compares mgqpy with other libraries that evaluate MongoDB filter
queries without a server. Nothing here is imported by mgqpy. Results are in
[`results/RESULTS.md`](results/RESULTS.md), generated by [`report.py`](report.py)
from the JSON files beside it. Those JSON files are slimmed: they keep versions,
hardware, configuration, hashes, per-case statuses, medians, paired ratios and the
compatibility summary, and omit raw timing samples and per-query corpus results
(about 24 MB; rerun `compat.py` to get them). `benchmarks/report.py` generates
the versioned-snapshot tables in `benchmarks/README.md`; these results have a
different shape, so they have their own report script.

## Libraries

Surveyed on 2026-10-20 (PyPI, npm, GitHub, web search).

| Library | Version | Released | Entry point used |
| --- | --- | --- | --- |
| mgqpy | 1.0.2 (this checkout) | 2026-10-20 | `Query(q).test(d)` |
| mongomock | 4.3.0 | 2024-11-16 | `mongomock.filtering.filter_applies(q, d)`, which `Collection.find` calls |
| mongoquery | 1.4.3 | 2025-09-16 | `Query(q).match(d)` |
| mongo-query-match | 2.0.0 | 2025-02-02 | Fork of mongoquery with the same `Query(q).match(d)` and the same module name |
| montydb | 2.5.6 | 2025-11-01 | `montydb.engine.queries.QueryFilter(q)(d)`, which the cursor calls; BSON on, default `mongo_version` 4.2 |
| tinymongo | 1.3.1 | 2026-09-21 | `validate_filter_operators(q)`, then `matches_filter(d, q)`, its full-scan matcher |
| mongita | 1.2.0 | 2023-04-03 | `_validate_filter(q)`, then `_doc_matches_slow_filters(d, q)`, its unindexed `find` path |
| sift (npm) | 17.1.4 | 2026-10-08 | `sift(q)(d)` |
| mingo (npm) | 7.2.5 | 2026-10-15 | `new Query(q).test(d)` |

Montydb, tinymongo and mongita are embedded databases, and mongomock is a test
double. For these, the comparison uses the matcher their `find` calls on each
document. A spot check compared that matcher with each library's real
in-memory `collection.find`, using every seventh corpus query (823 queries):

- mongomock and mongita: identical.
- tinymongo: one difference (`{"x": {"$exists": {}}}`).
- montydb: 17 differences, all involving NaN or regex values after its BSON
  round trip. In none of them was `find` closer to MongoDB than the matcher.

Montydb's `mongo_version="4.4"` mode gave the same results as its default, so
it is reported once.

Excluded:

- **mongomock-motor**: an async wrapper around mongomock's matcher.
- **pymongo_inmemory** (and similar test helpers): runs a real `mongod`, so it
  is not offline evaluation.
- **ya** 0.0.6: on import it calls itself a partial implementation and
  recommends mongoquery. It has no array semantics and spells `$ne` as `$neq`.
- **pymdict**: needs a MongoDB server.
- **dictquery**, **jsonquery** and **filtrate**: use their own syntax or build
  SQL queries; they do not match MongoDB filters.

## Compatibility method

[`corpus.py`](corpus.py) builds a deterministic corpus of documents and filter
queries. It has three parts:

- **`probe`**: the real-server differential from the mgqpy 1.0.2 review,
  reproduced exactly (415 documents, 4,974 queries, `random.Random(50023)`).
  mgqpy was developed against it, so its result there is expected rather than
  independent.
- **`new`**: 91 documents and 746 queries written for this comparison. They
  cover cross-type numbers, numeric strings, Unicode, `$type`, regex options,
  logical combinations, `$not`, null and missing fields, nested arrays and
  `$elemMatch`.
- **`invalid`**: 36 hand-written queries that MongoDB rejects.

[`corpus_docs.py`](corpus_docs.py) is a separate, independent set: 74 filters
and their sample documents taken from the MongoDB manual's query tutorials and
operator pages (each group links its page). Pages whose examples use the large
`sample_mflix` dataset (`$type`, `$exists`) get small stand-in documents with the
same field shapes. Expected results come from the servers, not from the page text.

The report leads with the `new` queries and the manual examples, the two sets no
library here was developed against; the full corpus is a labelled secondary row.

[`compat.py`](compat.py) runs every query with `find` on each MongoDB server and
in each library, one subprocess per library. A library agrees on a query only
if it returns exactly the server's set of matching documents. A wrong document
or any exception counts as a disagreement. Results are grouped by:

- operator;
- path shape;
- operand type, for equality, ranges, `$in`/`$nin` and `$all`;
- corpus origin.

For queries MongoDB rejects, the report records whether the library also
rejects them. A separate set of canonical queries checks operator coverage.

The JavaScript libraries run the same corpus in Node, through
[`js/compat.mjs`](js/compat.mjs). Values are encoded as tagged JSON and decoded
to `Date`, `RegExp`, `Buffer`, `NaN` and `Infinity`. Documents and queries that
JavaScript cannot represent unchanged are excluded from the JavaScript rows and
counted: integers beyond 2⁵³, verbose regex flags, and objects whose
integer-like keys JavaScript would reorder.

## Performance method

[`perf.py`](perf.py) reuses `measure`, `load`, `activate` and `hardware` from
[`../run.py`](../run.py) and the 311 cases in [`../cases.py`](../cases.py),
with the defaults described in [`../README.md`](../README.md#paired-measurements-and-noise).
mgqpy is the baseline, and a second independent mgqpy import is the
identical-source control.

A case is timed for a library only if both conditions hold:

- every MongoDB server returns the case's literal expected boolean;
- the library returns that same `bool`.

The report also drops a case for a library if the library gets any other case in
the same hit/miss family wrong (for example `or-early`, `or-last`, `or-miss`).
Without this rule, a library could count a miss that is right for the wrong
reason: mongita treats `$or` as a field name, so every `$or` query misses.
The JSON keeps both counts.

Because ratios are against mgqpy, a case is timed only where the servers return
the case's expected boolean, which is mgqpy's answer; the Node appendix uses the
same rule. This excludes 35 cases whose Python values cannot be encoded as BSON
(`date`, `Decimal`, `UUID`, integers outside int64, `complex`), and
`regex-unicode-class`: a valid query (`^\w+$` on `"äpfel"`) where MongoDB 7 and 8
return false, mgqpy returns true and sift and mingo return false. That mgqpy
difference is counted as an mgqpy miss in the compatibility tables. Wrong answers
and exceptions are never timed.

This is a survey of one corpus and one set of workloads, mostly mgqpy's own
development fixtures plus independent MongoDB manual examples, not a general
ranking. The saved results were measured on the mgqpy 1.0.2 runtime, which 1.0.3
does not change.

Operations:

- **`match`**: reuses the library's prepared object. mongomock has no
  preparation step, so its `match` includes interpreting the filter on every
  call.
- **`construct`**: only the library's preparation step.
- **`single-use`**: preparation and matching together.

[`perf_js.py`](perf_js.py) and [`js/perf.mjs`](js/perf.mjs) apply the same
cases, eligibility rule and block structure to sift and mingo in Node. sift is
the baseline there, and a second sift module instance is the control. Node
timings use `process.cpuUsage`, run JIT-compiled code after warm-up, and call
`gc()` between blocks rather than disabling GC. Do not compare them with the
Python numbers.

The headline Python run is CPython 3.11; a CPython 3.13 run of the same harness
is reported as a check. Compatibility does not depend on the Python version and
runs once. Comparisons are valid only within one run on the same machine. Hardware,
versions and harness hashes are recorded in each JSON file.

## Running

Needs MongoDB 7 and 8 on loopback ports (here 27017 and 27018), Python 3.11+,
and Node 20+ for the JavaScript rows.

```sh
uv venv /tmp/cmpvenv && VIRTUAL_ENV=/tmp/cmpvenv uv pip install -r benchmarks/compare/requirements.txt
# mongo-query-match installs the same `mongoquery` module, so keep it apart:
VIRTUAL_ENV=/tmp/cmpvenv uv pip install --target /tmp/mqm-target --no-deps -r benchmarks/compare/requirements-mongo-query-match.txt
export MQM_TARGET=/tmp/mqm-target
(cd benchmarks/compare/js && npm ci --ignore-scripts)

/tmp/cmpvenv/bin/python benchmarks/compare/compat.py --ports 27017 27018 --output benchmarks/compare/results/compat.json
/tmp/cmpvenv/bin/python benchmarks/compare/perf.py --ports 27017 27018 --cpu 0 --output benchmarks/compare/results/perf.json
/tmp/cmpvenv313/bin/python benchmarks/compare/perf.py --ports 27017 27018 --cpu 0 --output benchmarks/compare/results/perf-3.13.json
/tmp/cmpvenv/bin/python benchmarks/compare/perf_js.py --ports 27017 27018 --cpu 0 --output benchmarks/compare/results/perf-js.json
/tmp/cmpvenv/bin/python benchmarks/compare/report.py benchmarks/compare/results
```

Run the timing scripts one at a time on an otherwise idle machine. The committed
JSON was slimmed after each run by dropping `runs[*].rows` (perf) and the
per-query `results` lists (compat); `report.py` reads either form.
`/tmp/cmpvenv313` is a second virtualenv with the same requirements on CPython 3.13.
